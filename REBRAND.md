# Rebrand: Thuki → Veilura (1.0.0)

> **Status:** Phase 1 rebrand, committed on branch `rebrand-veilura`.
> **Rule for future edits:** do not "fix" the remaining `Thuki` mentions back.
> Every one is intentional — see §9 for the full hit list with justifications.
> The upstream name survives only where this document says it must.

## 1. Name rationale

**Veilura** — pronounced **VAY-loo-rah**.

- **Veil** = privacy. The app runs locally, keeps conversations on-device, and
  never sends prompts to a vendor cloud. The veil is what the user hides
  behind.
- **Aura** = presence. The app is a floating overlay that is present wherever
  the user works, summoned by a keystroke, without switching apps.
- The old name, Thuki, came from Vietnamese *thư ký* ("secretary"). That
  etymology is dropped: the system prompt, README, and design system no
  longer reference it, and the product no longer leans on a language-specific
  pun. "Secretary" remains an accurate plain-language description of what
  the app does, but it is not the brand.

## 5. Migration design (Thuki → Veilura data)

### Why a migration is needed

Tauri resolves the app dir from the bundle ID, so the rename alone moves
the app dir:

- Old: `~/Library/Application Support/com.quietnode.thuki/`
- New: `~/Library/Application Support/com.veilura.app/`

On macOS, Tauri's `app_config_dir()` and `app_data_dir()` resolve to the
**same** directory, so one copy covers `config.toml`, `veilura.db`,
`models/`, `traces/`, and the updater sidecar.

### Rules (implemented)

1. **Trigger:** first launch only, and only when the new dir is absent or
   empty. A non-empty new dir wins — nothing is copied.
2. **COPY, never move/delete.** The old Thuki dir is left completely
   untouched: the old app (if still installed) keeps working, and the
   migration is re-runnable.
3. **DB renamed in flight.** Legacy `thuki.db` (+ `-wal` / `-shm` /
   `-journal` sidecars) lands as `veilura.db` (+ sidecars). Every other
   entry keeps its name.
4. **Symlinks are skipped, never followed.**
5. **Best-effort.** Any I/O error is logged and startup continues with
   fresh state — migration must never fail launch.

### Code

- `src-tauri/src/config/migrate.rs` —
  `LEGACY_BUNDLE_ID = "com.quietnode.thuki"`,
  `migrate_legacy_app_support_dir(new_dir, old_dir)`, 5 unit tests
  (copy + DB rename, skip-when-non-empty, copy-into-empty-dir,
  no-op-when-old-missing, symlink skip).
- `src-tauri/src/lib.rs` — wired at the top of `setup()`, **before** config
  load and before anything else reads the new dir. Logs
  `veilura: [migration] …` to stderr.
- `src-tauri/src/database.rs` — `DB_FILE_NAME = "veilura.db"`,
  `LEGACY_DB_FILE_NAME = "thuki.db"`. The pre-existing `~/.thuki/thuki.db`
  (pre-Tauri location) move-migration is kept as-is and now targets
  `veilura.db`.

### Explicitly NOT migrated

- **Keychain provider API keys.** The service name changes with the bundle
  ID (`com.veilura.app.provider-api-key`), so keys stored under the old
  service are not visible to Veilura. Users re-enter provider keys once.
  (Migrating Keychain entries would require enumerating the old service;
  out of scope for Phase 1.)
- **TCC grants (Accessibility / Screen Recording).** macOS ties these to the
  code signature / bundle ID. The existing `tccutil reset` + relaunch flow
  in the updater path still applies on upgrade; users may need to re-grant.
- **The old dir itself.** Never deleted. Users remove
  `~/Library/Application Support/com.quietnode.thuki/` manually if they
  want the disk space back.

## 6. Updater, releases, and infrastructure that does NOT exist yet

- **Updater endpoint is a placeholder.** `tauri.conf.json`
  `plugins.updater.endpoints` and `DEFAULT_UPDATER_MANIFEST_URL`
  (`src-tauri/src/config/defaults.rs`) point at
  `https://veilura.online/updates/latest.json`. Nothing serves that URL.
  Automatic checks fail closed (the poller treats a failed check as
  transient, keeps any previously known update, and never clears state).
- **The committed `pubkey` is the upstream Thuki key.** It is retained so
  the config stays well-formed, but it **must not** be used for Veilura
  releases. Before the first real release, generate a **fresh updater
  keypair**, put the private key in GitHub Actions secrets, and replace the
  pubkey. See the banner at the top of `docs/release-process.md`.
- **Intel DMG: updater stays off.** The frozen workflow
  `.github/workflows/build-intel-dmg.yml` sets
  `.plugins.updater.active = false` via `jq` at build time (same approach
  as nightly). An Intel build must never self-update into an arm64
  artifact, and no update server exists anyway. Re-download the Intel DMG
  for updates.
- **No GitHub repo / secrets / confidential backup exist yet.** Everything
  in `docs/release-process.md` (Actions secrets, `veilura/veilura-confidential`,
  signed-release flow) is the *intended* pipeline, flagged as not-wired-up
  in that doc's banner.
- **No install script.** `veilura.online/install.sh` is a placeholder;
  README and `docs/install.md` say so and point at the manual-DMG and
  build-from-source paths.
- **Demo videos** in README (`github.com/user-attachments/…`) are upstream
  Thuki recordings. Keep until Veilura recordings exist; do not claim they
  show Veilura.
- **README CI badge** targets `pr-pipeline.yml`, which does not exist in
  this tree (pre-existing inconsistency, renamed to the placeholder repo).
- **Star-history chart** in README points at the placeholder repo.

**icns caveat.** `icon.icns` was built on Linux with the pure-Python
writer (`scripts/build-icns.py`), whose elements carry PNG payloads.
That is accepted by modern macOS (11+), but the native `iconutil` output
(JPEG 2000 payloads for large slots) is the gold standard. **Before a
release, regenerate on macOS:** `scripts/build-icns.sh` (uses `iconutil`
when present, else the Python writer) and verify in Finder / with
`sips`. The old `tray-update@2x.png` was deleted (unused; `lib.rs` only
references `tray-update.png`).

### Tray icon (macOS menu-bar / top bar) — verified

The menu-bar / tray icon is the **new Veilura mark**, not the old Thuki mark.
Exact assets (the only two tray icon files referenced anywhere in code):

| File | State | Used when |
| --- | --- | --- |
| `src-tauri/icons/tray.png` (44×44) | Normal | No update available |
| `src-tauri/icons/tray-update.png` (44×44) | Update available | Same mark + teal dot badge (bottom-right) |

Wiring (`src-tauri/src/lib.rs`): `TrayIconBuilder` loads
`include_bytes!("../icons/tray.png")` with `.icon_as_template(true)` —
a proper monochrome macOS template image, so macOS tints it for light/dark
menu bars. `refresh_tray()` swaps to `tray-update.png` when an update is
available. No other tray/menubar asset exists in the tree (`tauri.conf.json`
has no tray icon reference; the stale `tray-update@2x.png` was deleted).

**How verified (this phase, visual + byte-level):**

1. Decoded both PNGs and composited them onto dark and light backgrounds:
   both render the new mark — three white veil/aurora arcs + spark — with a
   dark outline underlay that keeps the mark legible on a light menu bar
   even if the template flag is ever dropped.
2. Extracted the pre-rebrand `tray-update.png` from git history
   (`git show HEAD~1:src-tauri/icons/tray-update.png`, 128×128) and rendered
   it the same way: it shows the **old Thuki mascot** (hamster/secretary
   character with monocle, bow tie, arrow) — completely different artwork,
   confirming the old mark is gone from the tray path. New files are 44×44
   with a different opaque-pixel footprint (345 / 478 opaque px vs 11,068
   for the old 128×128 file).
3. Confirmed via `git grep` that `lib.rs` references only these two files
   for the tray icon.

**Tray icon note.** The tray mark is white with a dark outline so it stays
legible even if a `set_icon` call ever drops the template flag (macOS
renders template images from the alpha channel, so the outline just
thickens the silhouette slightly).
